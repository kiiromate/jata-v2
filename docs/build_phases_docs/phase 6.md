# JATA V2 - Phase 6 Build Plan: Security Hardening & RLS Implementation

**Objective**: To resolve the database schema synchronization issue, establish a local, version-controlled schema, and implement state-of-the-art Row Level Security (RLS) policies to protect all user data.

**Strategy**: We will perform a one-time "schema dump" to capture the remote database's current state. We will use this dump to create a clean, initial local migration. Once the local environment is in sync, we will create a second migration to apply the necessary RLS policies.

---

### **Step 1: Synchronize Remote Schema Locally**

**Goal**: Fix the "history mismatch" error by creating a definitive local copy of the remote schema.

**Instructions**:
1.  **Dump Remote Schema**: Open your terminal in the project root (`/jata`) and run the following Supabase CLI command. This command inspects the *live* remote database and writes its entire structure to a single SQL file, ignoring its migration history.
    ```bash
    supabase db remote dump --schema-only -f supabase/schema_dump.sql
    ```
2.  **Reset Local Supabase**: Completely stop your local instance to ensure no old data or states persist.
    ```bash
    supabase stop --no-backup
    ```
3.  **Prepare Local Migrations Folder**: Navigate to the `supabase/migrations` directory. Delete any existing files inside it. This ensures we are starting from a clean slate.
4.  **Create Initial Migration File**: Run the migration command to create a new, empty migration file. This will be our new "ground truth."
    ```bash
    supabase migration new initial_schema_and_rls
    ```
5.  **Populate the Migration File**:
    -   Open the newly created file inside `supabase/migrations` (e.g., `<timestamp>_initial_schema_and_rls.sql`).
    -   Open the `supabase/schema_dump.sql` file you created in step 1.
    -   **Copy the entire contents** from `schema_dump.sql` and **paste it** into your new `<timestamp>_initial_schema_and_rls.sql` migration file.

### **Step 2: Generate and Add RLS Policies**

**Goal**: Create the SQL policies that will protect your users' data.

**Action**: Use the Gemini CLI to generate the required RLS SQL.

**CLI Command**:
```bash
gemini -p "Generate the PostgreSQL SQL code to secure the JATA database according to the RLS architecture guide. The script must: 1. Enable Row Level Security on the 'applications' and 'scrape_configs' tables. 2. Create a policy named 'allow_all_for_owner' on the 'applications' table for ALL actions (SELECT, INSERT, UPDATE, DELETE) using the condition 'auth.uid() = user_id'. 3. Create an identical policy named 'allow_all_for_owner' on the 'scrape_configs' table for ALL actions using the same condition. Ensure the policies are created WITH CHECK for INSERT and UPDATE."
```

**Instructions**:
1.  **Append to Migration File**: Copy the SQL code generated by Gemini.
2.  **Paste it at the very end** of your `<timestamp>_initial_schema_and_rls.sql` migration file. Now this single file contains both your database structure and its security rules.

### **Step 3: Apply Migrations and Verify**

**Goal**: Start the local environment with the new, unified migration file to create a secure, synced local database.

**Instructions**:
1.  **Start Supabase Locally**: Run the start command. Supabase will detect the new migration file and apply it automatically.
    ```bash
sh
supabase start
```
2.  **Verify in Supabase Studio**:
    -   Navigate to your local Supabase Studio (the URL will be in the `supabase start` output).
    -   Go to the **Table Editor**. Confirm your `applications` and `scrape_configs` tables exist.
    -   Go to **Authentication -> Policies**. Confirm that RLS is enabled for both tables and that the `allow_all_for_owner` policies are present.

You have now successfully synchronized your remote schema, established a local version-controlled migration history, and implemented the foundational security for your application. All future database changes must now be done by creating new migration files (`supabase migration new ...`).
